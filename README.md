## Описание проекта

Проект использует датасет **Video Game Sales & Metacritic Intelligence 1980–26** (исходно около 50 000 записей). Задача — предсказать мировые продажи видеоигры по характеристикам игры, её издания и оценкам.

Работа выполняется поэтапно:

- **ЛР1:** подготовка данных и EDA;
- **ЛР2:** обучение, сравнение и регистрация моделей в MLflow;
- **ЛР3:** получение сохранённой модели из MLflow, реализация API на FastAPI, упаковка в Docker;
- **ЛР4:** генерация нагрузки, экспорт метрик, мониторинг в Prometheus и Grafana.

## Технологии

Python, pandas, NumPy, scikit-learn, Jupyter Notebook, Optuna, MLflow, FastAPI, Uvicorn, Docker, Docker Compose, Prometheus и Grafana.

Для контейнера ML-сервиса использовались совместимые версии зависимостей: `numpy==1.26.4`, `scikit-learn==1.5.2`, `scipy==1.13.1`, `cloudpickle==3.1.2`. При пересборке следует ориентироваться на фактические файлы зависимостей сервиса.

## ЛР3 — развёртывание модели в FastAPI и Docker

### Цель и реализованный результат

В ЛР3 обученная в ЛР2 модель была извлечена из MLflow, сохранена как `services/models/model.pkl`, подключена к REST API на FastAPI и упакована в Docker. Использовался образ `game_sales_service:1`; в ЛР4 создана версия `game_sales_service:2`. Работоспособность API подтверждалась ответом HTTP 200.

### Назначение файлов

| Файл | Назначение |
|---|---|
| `services/ml_service/main.py` | Создаёт FastAPI-приложение, определяет маршруты `/` и `/api/prediction`, проверяет структуру запроса |
| `services/ml_service/api_handler.py` | Класс `FastAPIHandler`: загружает модель с помощью `cloudpickle`, формирует DataFrame, вызывает `predict` |
| `services/ml_service/requirements.txt` | Зависимости именно Docker-контейнера API, отдельно от корневого `requirements.txt` |
| `services/ml_service/Dockerfile` | Сборка образа на `python:3.11-slim`, установка библиотек, запуск Uvicorn на `0.0.0.0:8000` |
| `services/models/get_model.py` | Получение артефакта модели из MLflow по run ID |
| `services/models/model.pkl` | Сериализованная модель, подключаемая к контейнеру как том |

Для совместимости сохранённой модели использовались `numpy==1.26.4`, `scikit-learn==1.5.2`, `scipy==1.13.1`, `cloudpickle==3.1.2`. Полный список зависимостей необходимо брать из фактического `services/ml_service/requirements.txt`.

### Контракт API предсказаний

`POST /api/prediction?item_id=123` принимает целочисленный `item_id` в URL и JSON-тело с объектом `features`, содержащим признаки видеоигры. `FastAPIHandler` преобразует признаки в однострочный `pandas.DataFrame` и передаёт их в модель. Если модель содержит `feature_names_in_`, столбцы упорядочиваются согласно ожидаемому порядку.

**Форма тела запроса** (схема; значения и полный набор признаков нужно брать из фактического входного датасета/генератора запросов):

```json
{
  "features": {
    "genre": "<категория из обучающего датасета>",
    "publisher_tier": "<категория из обучающего датасета>",
    "launch_price_usd": 59.99,
    "metacritic_score": 85
  }
}
```

Это **иллюстрация структуры**, а не гарантированно работоспособный запрос: модель может требовать дополнительные признаки. Для воспроизводимого теста нужно скопировать полный `features` из рабочего запроса генератора `services/requests/send_requests.py` или из Swagger UI.

Пример команды с файлом `request.json`, содержащим **полный** набор признаков:

```bash
curl -i -X POST 'http://localhost:8000/api/prediction?item_id=123' \\
  -H 'Content-Type: application/json' \\
  --data @request.json
```

**Фактическая структура ответа реализации `main.py`:**

```json
{"item_id": 123, "price": 0.7637315626006276}
```

Число здесь — пример формата ответа из методички, **не результат конкретного запуска**. В задании в одном месте используется ключ `predict`, но показанный преподавателем пример содержит `price`; текущий `main.py` возвращает именно `price`. При проверке следует ориентироваться на реально реализованный API и при необходимости согласовать имя поля с преподавателем.

### Метрики и Prometheus

FastAPI предоставляет метрики в формате Prometheus через endpoint `/metrics`. В ходе работы проверялись счётчики HTTP-запросов, метрики времени обработки и распределения предсказаний (гистограмма).

Проверка доступности метрик с хоста:

```bash
curl -s http://localhost:8000/metrics | head -n 30
```

В интерфейсе Prometheus (`http://localhost:9090`) можно проверить состояние цели:

```promql
up{job="ml_service"}
```

**Ожидаемый результат:** `1` — Prometheus успешно собирает метрики с FastAPI. В ходе ЛР4 значение `1` было получено.

Проверка общего количества HTTP-запросов по кодам ответа:

```promql
sum by (status) (http_requests_total)
```

Частота запросов к endpoint предсказания за минуту:

```promql
sum(rate(http_requests_total{endpoint="/api/prediction"}[1m])) * 60
```

Это скорость запросов, оцененная по скользящему окну в одну минуту, а не точное число запросов за календарную минуту.

### Подключение Grafana

4. Нажать **Save & test**.

6. Для ввода PromQL раскрыть запрос `A` и переключить редактор в режим **Code**; затем нажать **Run queries**.
7. Сохранить панель, затем нажать **Save** в правом верхнем углу **самого дашборда**. Рекомендуемое имя: `ML Model Monitoring`.

### Реализованные и проверенные панели

**1. Prediction requests per minute** — частота запросов к модели:

```promql
sum(rate(http_requests_total{endpoint="/api/prediction"}[1m])) * 60
```

В Grafana отображался график с поступающими запросами.

**2. HTTP Errors 4xx and 5xx** — число ошибок по двум сериям за скользящие пять минут:

Серия `4xx`:

```promql
sum(increase(http_requests_total{status=~"4.."}[5m]))
```

Серия `5xx`:

```promql
sum(increase(http_requests_total{status=~"5.."}[5m]))
```

График показывал ошибки; после ручного обновления (**Refresh**) отобразились новые тестовые значения.

**Дополнительные визуализации:** в обсуждавшихся требованиях ЛР4 упоминалось не менее **пяти графиков Grafana**. По подтверждённым результатам здесь документированы **две панели**. Остальные панели следует добавить и описать после фактического создания; не нужно считать требование выполненным автоматически.

### Проверка обработки ошибок (пункт 25.3)

Для проверки счётчиков HTTP-ошибок выполнены по пять запросов на несуществующий адрес и на тестовый endpoint ошибки сервера:

```bash
for i in $(seq 1 5); do
  curl -s -o /dev/null -w '4xx: HTTP %{http_code}\n' \
    http://localhost:8000/nonexistent

  curl -s -o /dev/null -w '5xx: HTTP %{http_code}\n' \
    http://localhost:8000/test-error

  sleep 1
done
```

Фактический результат теста: **пять ответов HTTP 404 и пять ответов HTTP 500**. После обновления панели Grafana новые ошибки стали видны на графике.

> Endpoint `/test-error` используется для тестирования ошибок и может отсутствовать в финальной версии приложения, если тестовый маршрут был удалён. Не следует использовать его как рабочий endpoint предсказаний.

### Сохранение результатов мониторинга

Данные Prometheus и Grafana хранятся в именованных Docker-томах:

- `services_prometheus_data` — временные ряды Prometheus;
- `services_grafana_data` — настройки и данные Grafana.

Обычная остановка контейнеров **не должна удалять эти тома**. Не выполняйте `docker compose down -v`, если нужно сохранить историю мониторинга и дашборды.

Если методичка требует приложить JSON-экспорт дашборда, его необходимо отдельно выгрузить через интерфейс Grafana и добавить в репозиторий. **Сам факт сохранения дашборда в Grafana не означает, что JSON уже экспортирован.**

### Остановка и повторный запуск

```bash
cd ~/My_proj/services

```

### Дополнения к требованиям ЛР4: артефакты, графики и уровни мониторинга

**Скрипт нагрузки.** В проекте используется `services/requests/send_requests.py` (в методичке предложено имя `requests.py`, но переименование позволяет избежать конфликта с Python-пакетом `requests`). Скрипт отправляет запросы к сервису `ml_service` по внутренней сети Compose с паузами. В папке `requests` по заданию должны находиться минимальный `requirements.txt` и Dockerfile с закомментированными примерами `docker build` и `docker run`. Фактические имена образа и команды следует брать из `compose.yml` и Dockerfile.

**Конфигурация Prometheus.** Файл `services/prometheus/prometheus.yml` определяет задания сбора метрик (scrape jobs), включая обращение к `ml_service` по внутреннему имени Docker-сервиса. Проверка `up{job="ml_service"} == 1` подтверждает доступность цели для Prometheus. Наличие HTTP-метрик и гистограммы предсказаний проверяется на `/metrics`.

**Гистограмма предсказаний.** Требование пункта 10 ЛР4 — отдельная метрика типа histogram для результатов модели. Гистограмма предоставляет серии `_bucket`, `_sum` и `_count`; конкретное имя метрики и границы корзин нужно сверить с фактическим кодом. Для построения графика распределения используются серии вида `ИМЯ_ГИСТОГРАММЫ_bucket`, сгруппированные по метке `le`. Не следует подменять распределение предсказаний обычной гистограммой HTTP-задержек.

**Обязательные скриншоты Prometheus (пункт 14):**

1. Гистограмма предсказаний модели.
2. Частота запросов к API в минуту.
3. Количество HTTP-ошибок 4xx и 5xx двумя линиями на одном графике.

После сохранения реальных скриншотов в репозитории вставить их сюда, например `![Частота запросов](services/prometheus/screenshots/requests_per_minute.png)`. **Скриншоты пока не вложены в этот README, и их наличие в репозитории не подтверждено.**

**Минимум пять панелей Grafana (пункт 24).** Ниже — состав дашборда, который покрывает требуемые уровни мониторинга. Первые две панели уже проверялись в ходе выполнения работы; остальные необходимо создать и проверить:

| Панель | Уровень | Источник / PromQL | Статус |
|---|---|---|---|
| Prediction requests per minute | Прикладной | `sum(rate(http_requests_total{endpoint="/api/prediction"}[1m])) * 60` | Проверена |
| HTTP Errors 4xx and 5xx | Прикладной, ошибки | Два запроса `sum(increase(http_requests_total{status=~"4.."}[5m]))` и `sum(increase(http_requests_total{status=~"5.."}[5m]))` | Проверена |
| API availability | Инфраструктурный / доступность | `up{job="ml_service"}` | Требуется создать панель |
| HTTP request duration | Прикладной, производительность | `rate(http_request_duration_seconds_sum[5m]) / rate(http_request_duration_seconds_count[5m])` — **только если эти серии реально существуют** | Требуется проверить имя метрики и создать панель |
| Prediction distribution | Мониторинг поведения модели | Histogram предсказаний: серия `_bucket` с группировкой по `le`; точное имя берётся из `/metrics` | Требуется создать панель |

Панель распределения предсказаний позволяет наблюдать за изменениями выходов модели, но **без эталонных ответов не измеряет точность предсказаний**, а без сравнения распределений за разные периоды не доказывает data shift. Раздел PostgreSQL/pgAdmin в методичке помечен как необязательный; без БД подключение к ней и связанные графики не требуются.

**Проверка нагрузки (пункт 25).** Генератор `requests` создаёт обычный поток обращений. Для проверки ошибок вручную выполнялись пять запросов к `/nonexistent` (HTTP 404) и пять к `/test-error` (HTTP 500); после Refresh Grafana показала новые значения. Тестовый маршрут `/test-error` не является рабочим API модели.

**Скриншот общего дашборда (пункт 26).** После создания всех пяти панелей необходимо сохранить единый скриншот, поместить его, например, в `services/grafana/screenshots/dashboard.png` и вставить в README:

```markdown

```

Каждая панель описана в таблице выше с указанием её уровня мониторинга. Вставка ссылки не заменяет сам файл изображения.

**Экспорт дашборда (пункт 27).** В Grafana открыть нужный дашборд → **Share / Export** (название меню зависит от версии) → экспортировать JSON → сохранить в репозитории как `services/grafana/ml_model_monitoring.json`. Проверить, что файл можно импортировать в Grafana. Само сохранение дашборда в интерфейсе **не создаёт** JSON в каталоге проекта.

**Необязательная БД.** PostgreSQL и pgAdmin не развёрнуты в подтверждённом составе четырёх сервисов. Поэтому структура таблиц, SQL-подключение и хранение входных данных в БД здесь не заявляются как реализованные.

## Проверка и диагностика

| Проблема | Что проверить |
|---|---|
| FastAPI не отвечает | `sudo docker compose ps` и `sudo docker compose logs --tail=100 ml_service` |
| Запросы к модели не проходят | URL `/api/prediction`, метод `POST`, параметр `item_id` и логи API |
| В Prometheus нет данных | `up{job="ml_service"}`, доступность `/metrics`, настройки сбора |
| В Grafana нет графика | Источник данных Prometheus, режим **Code**, **Run queries**, диапазон времени |
| Новые ошибки не видны | Выбрать **Last 15 minutes** и нажать **Refresh**; учесть окно `[5m]` |
| Docker не запускается из-за нехватки места | `df -h /`, `sudo docker system df`; не удалять рабочие образы и тома без проверки |

Во время выполнения ЛР4 на виртуальной машине Ubuntu корневой раздел объёмом **24 ГБ** заполнялся до 100%. После очистки кэша Snap свободное место восстановлено примерно до **2 ГБ** (заполнение **92%**). Docker-сервисы продолжили работать. Это эксплуатационное замечание, а не обязательный этап лабораторной.

Для проверки места:

```bash
df -h /
sudo docker system df
```
